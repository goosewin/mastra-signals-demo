Beyond the Demo:
Steering Live Agents in Production

Mastra Signals — talking to agents that are already running.
Dan Goosewin · github.com/goosewin

Every agent demo you've ever seen

prompt in → tokens out → applause

  • One user. One request. One response.
  • The world politely stops changing while the agent runs.
  • Nobody interrupts. Nothing breaks. Nothing arrives.

That's not an agent. That's a slow function call.

Then you ship it

Production is rude.

  • A webhook fires 40 seconds into the run — CI fails, a page triggers, a customer replies.
  • The user watches the stream and goes "no no no, not that".
  • Your options today: ✕ kill the run and re-prompt (lose all progress)  ·  ✕ poll and cram context in up front (token soup)  ·  ✕ build your own agent message bus (there goes the quarter)
Mastra Signals

Talk to a running agent.

sendMessage()joins the active loop mid-run — or wakes an idle thread
queueMessage()runs as the next turn, after the current run finishes
sendNotificationSignal()durable inbox for external events — webhooks, CI, Slack, email
sendStateSignal()thread-scoped state lanes — browser state, editor state, policy
sendSignal()low-level system context, incl. processor-emitted reactive signals
subscribeToThread()any client, anywhere, watches the same live stream
The whole trick, part 1

Steer it. Interrupt it.

// human changes their mind mid-run
agent.sendMessage(
  'Focus on the EU regions first.',
  { resourceId, threadId },
)
// webhook lands mid-run
agent.sendNotificationSignal({
  source: 'pagerduty',
  priority: 'high',
  summary: 'pg at 4% errors',
  dedupeKey: 'pd:pg:err',
}, { resourceId, threadId })

Active run? It's delivered into the loop. Idle thread? It wakes up. You don't care which.

The whole trick, part 2

Watch it from anywhere.

const sub = await agent.subscribeToThread({ threadId, resourceId })

for await (const chunk of sub.stream) {
  render(chunk)  // text deltas, tool calls, results — every subscriber sees it all
}

Threads are addressable. N browser tabs, a CLI, a Slack bot — same thread, same live stream.
One process: works out of the box. A fleet of instances: plug in Redis Streams pub/sub. Same code.

Under the hood

Threads are processes you can address.

  • Route: every signal resolves to wake / deliver / queue / persist — depending on whether the thread is running
  • Durability: notifications & state lanes live in memory/storage — agents catch up on what they missed
  • Scale: in-process pub/sub by default → Redis Streams for cross-instance delivery & leasing
  • Transport: built-in HTTP routes + SSE subscriptions — the demo UI is fetch() and EventSource, nothing else
What this unlocks

Agents that live in your systems, not in a chat box.

  • Webhook-driven agents — GitHub, PagerDuty, Stripe events steer running work
  • Multiplayer agents — whole team watches & steers one thread
  • Human-in-the-loop that doesn't block — steer when needed, not approve-every-step
  • Background agents with an inbox — long-lived threads that accumulate context for days
